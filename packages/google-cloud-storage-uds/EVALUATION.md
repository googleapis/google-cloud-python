# Experiment: Thin Python Cloud Storage SDK over a Rust Unix Domain Socket Sidecar and Zero-Copy Shared Memory

## Introduction

We evaluate whether a thin, pure-Python Google Cloud Storage client communicating with a standalone Rust gRPC server over a local Unix Domain Socket can match the throughput and CPU efficiency of an in-process Rust extension while lowering maintenance overhead across client languages. This document covers the regional HTTP and JSON data path for range reads, object uploads, and object listing against a regional bucket. We start with the motivation behind this sidecar experiment, followed by a high-level overview of the socket-based architecture and the zero-copy shared-memory design, after which we present our conclusions and architectural recommendations.

Maintaining handwritten retry state machines, checksum verification, connection pooling, and concurrent range readers across eight separate client library languages creates high engineering cost and subtle correctness bugs. Cloud Bigtable recently explored solving this problem by embedding a shared local gRPC sidecar server, allowing thin target-language clients to call a simplified service contract over a local Unix Domain Socket while delegating complex transport logic to a single shared core binary. We built a proof of concept in [packages/google-cloud-storage-uds](file:///home/princer_google_com/dev/google-cloud-python/packages/google-cloud-storage-uds) to test whether this same local sidecar architecture works for high-bandwidth Google Cloud Storage workloads in Python, comparing it directly against our existing pure-Python client and our in-process Rust Foreign Function Interface extension.

To understand the difference between these architectures, we can compare them to standard operating system I/O models. An in-process Rust extension behaves like a shared library mapped directly into the application address space, where worker threads download network data and copy it into newly allocated Python byte objects in the same process. A local Unix Domain Socket sidecar behaves like a microkernel service or local database proxy: the Python process remains completely isolated from Rust memory management and Application Binary Interface constraints, but every payload byte must cross a local inter-process boundary. A zero-copy shared-memory sidecar combines both models in the same way that direct memory access ring buffers work in high-speed networking: the Unix Domain Socket carries only tiny control messages, while the Rust sidecar writes downloaded HTTP chunks directly into shared physical memory pages that Python reads in place with zero socket copies.

We already built and benchmarked the in-process Rust extension in a prior phase, and in this experiment we implemented both the socket-based sidecar and the zero-copy shared-memory sidecar in [main.rs](file:///home/princer_google_com/dev/google-cloud-python/packages/google-cloud-storage-uds/src/main.rs) and [client.py](file:///home/princer_google_com/dev/google-cloud-python/packages/google-cloud-storage-uds/google/cloud/storage_uds/client.py). Bidirectional gRPC streaming for zonal Rapid buckets and DirectPath session management are outside the scope of this document.

## High-Level Overview Approach

### The Unix Domain Socket gRPC Approach

- When the Python client initializes in [server_manager.py](file:///home/princer_google_com/dev/google-cloud-python/packages/google-cloud-storage-uds/google/cloud/storage_uds/server_manager.py), it checks whether the standalone Rust sidecar binary is already listening on a local Unix socket file in temporary storage, spawns the binary if needed, and establishes an asynchronous gRPC channel over that local socket.
- Although the socket path appears as a file in the filesystem, zero payload bytes ever touch the disk; the path serves only as a rendezvous address in the Linux virtual filesystem so the Python process and the Rust process can attach to the same in-memory kernel socket buffer, bypassing the TCP/IP network stack, port allocation, checksums, and loopback packet routing.
- We defined a simplified protobuf service contract in [storage_accelerator.proto](file:///home/princer_google_com/dev/google-cloud-python/packages/google-cloud-storage-uds/proto/storage_accelerator.proto) that exposes unary range reads, pipelined server-streaming range reads, object uploads, and paginated object listing, allowing any language with standard gRPC tooling to generate a thin client stub automatically.
- When we initially tested multi-megabyte reads over the Unix socket, we hit three protocol bottlenecks: Python gRPC set the HTTP/2 authority header to the raw file path containing slashes which the Rust HTTP/2 parser rejected, default 64 KiB HTTP/2 flow-control windows stalled transfers every 64 KiB, and unary RPCs forced the Rust server to finish downloading all ranges from Cloud Storage before sending the first byte to Python.
- We resolved those three socket bottlenecks in [main.rs](file:///home/princer_google_com/dev/google-cloud-python/packages/google-cloud-storage-uds/src/main.rs) and [client.py](file:///home/princer_google_com/dev/google-cloud-python/packages/google-cloud-storage-uds/google/cloud/storage_uds/client.py) by overriding the channel authority to localhost, raising the HTTP/2 stream and connection windows to 64 MiB and 256 MiB with 16 MiB frames, and streaming payloads of 4 MiB or larger in 4 MiB pipelined chunks so local socket transfers overlap with in-flight Cloud Storage downloads.
- Even after tuning HTTP/2 flow control and streaming, our live benchmarks in [bench_json_workload.py](file:///home/princer_google_com/dev/google-cloud-python/packages/google-cloud-storage-uds/benchmarks/bench_json_workload.py) showed that while the socket sidecar beat pure Python by 1.8x to 2.5x on small and medium concurrent reads (reaching 81.1 MiB/s on 100 x 64 KiB reads and 748.7 MiB/s on 64 x 1 MiB reads), it hit a hard throughput ceiling of 679.5 MiB/s on 16 x 16 MiB reads (256 MiB total) compared to 1,558.9 MiB/s for the in-process Rust extension.
- For example, when an analytics worker reads 16 ranges of 16 MiB each (256 MiB total) over the Unix socket, the system performs five separate memory copies totaling 1.28 GiB of memory traffic: the Rust HTTP reader copies chunks into a 4 MiB staging buffer, the protobuf encoder copies that buffer into an HTTP/2 frame, the kernel copies the frame from Rust user space into the kernel socket buffer, the kernel copies the frame out to the Python C-core gRPC receive buffer, and Python copies the payload into newly allocated byte objects, burning 3.47 CPU-seconds per GiB across both processes.

### The Zero-Copy Shared Memory Approach

- To eliminate the five socket and serialization copies without giving up the language-independent gRPC control plane, we split the local communication path into two planes: the Unix Domain Socket remains the control plane carrying only small metadata messages, while a shared-memory file in Linux tmpfs serves as the data plane where payload bytes reside.
- In [client.py](file:///home/princer_google_com/dev/google-cloud-python/packages/google-cloud-storage-uds/google/cloud/storage_uds/client.py), the Python client creates a persistent shared-memory arena backed by tmpfs RAM and maps it into the Python virtual address space as a shared read-write mapping; when requesting 16 ranges of 16 MiB, Python ensures the arena is at least 256 MiB and sends a 300-byte gRPC request over the Unix socket containing the bucket name, object name, byte ranges, and the path to the shared-memory file.
- In [main.rs](file:///home/princer_google_com/dev/google-cloud-python/packages/google-cloud-storage-uds/src/main.rs), the Rust sidecar maps that same tmpfs file into its own virtual address space so both processes point their hardware page tables at the exact same physical RAM pages, and assigns each of the 16 concurrent Tokio download tasks a non-overlapping 16 MiB offset slice inside the shared region.
- During our first shared-memory test, we noticed that opening and unmapping the shared-memory file on every RPC caused the Linux kernel to tear down page tables on unmap, trigger cross-core translation lookaside buffer shootdowns, and incur 65,536 minor page faults per 256 MiB call; caching the active memory mapping across RPCs inside the Rust server eliminated all page-table churn after the first call.
- As HTTP body chunks arrive from Cloud Storage, each Rust Tokio worker copies the decrypted bytes directly from the network buffer into its assigned offset in shared RAM, and once all 16 ranges complete, the server sends back a 128-byte gRPC response over the Unix socket listing only the actual byte lengths written.
- When Python receives that 128-byte response, it returns zero-copy memoryview slices pointing directly into the shared-memory arena without allocating Python byte objects or copying a single payload byte, lifting 16 x 16 MiB read throughput from 679.5 MiB/s to 2,002.9 MiB/s (4.35x faster than pure Python and 28% faster than the in-process Rust extension) while reducing Python CPU usage to 0.00 CPU-seconds per GiB and total CPU usage to 1.13 CPU-seconds per GiB.
- For object uploads, Python stages the payload into the shared-memory arena and sends a 100-byte control message over the Unix socket; the Rust server wraps the shared-memory slice in a custom reference-counted buffer owner and streams it directly to the HTTP socket without copying it onto the Rust heap, cutting 64 MiB upload CPU usage by 7.7x (from 3.33 down to 0.43 CPU-seconds per GiB) and raising upload throughput from 89.5 MiB/s to 139.4 MiB/s.

## Conclusion

A standard Unix Domain Socket gRPC sidecar is simple to generate across client languages and speeds up high-concurrency small reads by 1.8x to 2.5x over pure Python, but its five-copy serialization path caps throughput around 680 MiB/s and cannot saturate modern multi-gigabit cloud network interfaces on its own. Pairing that same Unix Domain Socket gRPC control plane with a persistent POSIX shared-memory data plane removes the socket copy bottleneck entirely, reaching 2,002.9 MiB/s on 16 x 16 MiB concurrent reads with zero Python CPU overhead and 1.13 CPU-seconds per GiB total CPU—matching or exceeding the in-process Rust extension while keeping the Python client 100% pure Python.

However, this shared-memory sidecar architecture carries three practical trade-offs that must be weighed before adopting it over an in-process extension: callers receiving zero-copy memoryview slices must consume them before the next batch read overwrites the shared arena, containerized environments like Docker default to a 64 MiB tmpfs limit that must be raised for large transfers, and managing an out-of-process daemon requires lifecycle tracking, crash recovery, and stale file cleanup. For Python workloads where prebuilt binary wheels are already standard, an in-process Rust extension offers simpler process lifecycle management and standard byte object semantics, whereas if our primary goal is sharing a single compiled transport binary across multiple languages (such as Python, Ruby, PHP, and Node.js), we should pair the Unix Domain Socket gRPC control channel with shared memory for all payloads of 1 MiB or larger.
